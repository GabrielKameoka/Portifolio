The problem

Sending a notification takes more than accepting a request. The provider may fail, processing may take time, and the user needs to know what happened to the message.

I built SinalVortex to explore that boundary: the API records the request, and the Worker processes it outside the HTTP cycle.

My contribution

In this personal project, I integrated a .NET API, Angular interface, PostgreSQL persistence, and Redis and Worker processing. The local demo connects them with Docker Compose and Mailpit.

I focused on making the message’s path traceable, from initial registration to delivery or failure.

How it works

  1. Receive and record. The Angular interface sends the notification to the API, which persists its state in PostgreSQL and publishes an item to the Redis queue.
  2. Process outside the API. The Worker consumes the queue and handles delivery. Retries and the DLQ handle failure paths according to the error type.
  3. Track. The interface checks status, while the monitor receives events via SignalR.
  4. Check local delivery. Mailpit captures email sent through the SMTP sandbox without forwarding it to real recipients.

Engineering decisions

Separate API and Worker

Delivery does not need to finish before the HTTP request ends. This separation lets me study the lifecycles of receiving and processing, while introducing communication between processes.

Distinct responsibilities for state and queue

PostgreSQL stores notifications and history; Redis organizes work to be consumed. This split requires care around consistency between persistence and enqueuing.

Visible failures

The DLQ keeps messages that could not be processed. Together with the monitor, it helps investigate a failure instead of reducing it to a generic error.

Local infrastructure for demos and tests

Docker Compose starts the demo services. Integration tests use Testcontainers to exercise real dependencies in isolated environments.

How to explore it

In the repository, with Docker and Compose available, run:

docker compose -f docker-compose.local.yml up --build

Open the interface on port 4200, create an account, and send an email notification. Follow the Inbox and monitor, then inspect the message captured by Mailpit on port 8025.

The repository walkthrough also covers failure scenarios and persistence checks.

Current limits

This is a local demo. SMTP acceptance means capture in Mailpit, not external email delivery.

SMS, WhatsApp, and Push have no implemented providers and demonstrate failure/DLQ behavior. Templates, CRM, inbound webhooks, and production deployment are not presented as finished features.

The project does not claim scale benchmarks or exactly-once delivery. Those would require further validation and design decisions.

What this project taught me

Separating services moves some complexity to their boundaries. Persistence, enqueuing, retries, and observability need to be designed together.

A useful demo must also be reproducible. Explaining how to start the environment and trigger a failure matters as much as showing the successful path.
