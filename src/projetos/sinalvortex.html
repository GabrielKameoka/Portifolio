O problema

Enviar uma notificação envolve mais do que aceitar uma requisição. O provedor pode falhar, o processamento pode levar tempo e o usuário precisa saber o que aconteceu com a mensagem.

Construí o SinalVortex para explorar essa fronteira: a API registra a solicitação e o Worker assume o processamento fora do ciclo HTTP.

Minha participação

No projeto autoral, trabalhei na integração entre API .NET, interface Angular, persistência PostgreSQL e processamento com Redis e Worker. A demonstração local conecta essas partes com Docker Compose e Mailpit.

O foco foi tornar o caminho da mensagem investigável: do registro inicial ao estado de entrega ou falha.

Como funciona

  1. Receber e registrar. A interface Angular envia a notificação à API, que persiste seu estado no PostgreSQL e publica o item na fila Redis.
  2. Processar fora da API. O Worker consome a fila e executa a entrega. Retry e DLQ tratam os caminhos de falha conforme o tipo de erro.
  3. Acompanhar. A interface consulta o estado, e o monitor recebe eventos via SignalR.
  4. Conferir a entrega local. O Mailpit captura o e-mail enviado pelo SMTP sandbox, sem encaminhá-lo a destinatários reais.

Decisões de engenharia

API e Worker separados

O envio não precisa terminar para encerrar a requisição HTTP. A separação permite estudar os ciclos de vida de recepção e processamento, ao custo de lidar com comunicação entre processos.

Estado persistido e fila com responsabilidades distintas

O PostgreSQL mantém notificações e histórico; o Redis organiza o trabalho a consumir. Essa divisão exige atenção à consistência entre persistir e enfileirar.

Falhas visíveis

A DLQ preserva mensagens que não puderam ser processadas. Junto do monitor, ajuda a investigar o motivo de uma falha em vez de tratá-la como um erro genérico.

Infraestrutura local para demonstrar e testar

Docker Compose reúne os serviços da demo. Testes de integração usam Testcontainers, permitindo exercitar dependências reais em ambientes isolados.

Como explorar

No repositório, com Docker e Compose disponíveis, execute:

docker compose -f docker-compose.local.yml up --build

Abra a interface na porta 4200, crie uma conta e envie uma notificação por e-mail. Acompanhe o Inbox e o monitor; confira a mensagem capturada no Mailpit, na porta 8025.

O roteiro no repositório também descreve cenários de falha e verificações de persistência.

Limites atuais

Esta é uma demonstração local. Aceitação pelo SMTP significa captura no Mailpit, não entrega de e-mail externo.

SMS, WhatsApp e Push não têm provedores implementados e demonstram falha/DLQ. Templates, CRM, webhooks inbound e deploy de produção não são apresentados como funcionalidades prontas.

O projeto não apresenta benchmarks de escala nem garantia de entrega exatamente uma vez. Esses pontos exigiriam validação e decisões adicionais.

O que esse projeto me ensina

Separar serviços desloca parte da complexidade para as fronteiras entre eles. Persistir, enfileirar, repetir e observar precisam ser pensados em conjunto.

Uma demo útil também precisa ser reproduzível. Explicar como iniciar o ambiente e provocar uma falha faz parte da entrega, tanto quanto mostrar o caminho que funciona.
